# Routes

File based routing with TanStack Router. `routeTree.gen.ts` is generated by the Vite plugin and is
committed, as the library recommends: a build then never depends on a generation step having run.

Three recipes cover every screen of M0. Copy them; do not invent a fourth.

## The context

`__root.tsx` loads `GET /api/me` once, with `ensureQueryData`, and puts it in the router context
next to the query client:

```tsx
export const Route = createRootRouteWithContext<{ queryClient: QueryClient }>()({
  beforeLoad: async ({ context }) => ({
    bootstrap: await context.queryClient.ensureQueryData(bootstrapQuery),
  }),
});
```

Every route below therefore reads `context.bootstrap` — the division, the menus, the languages, the
effective permissions — without a fetch of its own. A guard that fetched would be a guard that can
fail while the page is already drawing.

## Recipe 1 — a layout with a guard

`_public.tsx`, `_member.tsx`, `_staff.tsx`.

```tsx
export const Route = createFileRoute('/_staff')({
  beforeLoad: ({ context, location }) => {
    const me = context.bootstrap;
    if (!me.user) throw redirect({ href: `/auth/login?returnUrl=${encodeURIComponent(location.href)}` });
    if (!me.user.isStaff && !me.user.isSuperadmin) throw redirect({ to: '/forbidden' });
  },
  component: StaffLayout,
});
```

Two things are deliberate.

`href`, not `to`, for the login. `/auth/login` is a Kestrel endpoint, not a route of this
application: it needs a full navigation, and a router `to` would look for a page that does not exist.

Two different answers. "You are not signed in" sends you to the login; "this is not for you" sends
you to `/forbidden`. Sending the second to a login screen is how a member ends up in a loop with an
identity provider that will happily sign them in again.

## Recipe 2 — a list with typed search parameters

`_staff/staff.$dept.links.tsx`.

```tsx
export const Route = createFileRoute('/_staff/staff/$dept/links')({
  params: {
    parse: ({ dept }) => ({ dept: deptParam.parse(dept) }),
    stringify: ({ dept }) => ({ dept: deptParam.format(dept) }),
  },
  validateSearch: listSearchSchema,
  loaderDeps: ({ search }) => search,
  loader: ({ context, deps, params }) =>
    context.queryClient.ensureQueryData(linksListQuery(params.dept, deps)),
  component: LinksPage,
});
```

`listSearchSchema` (`shared/list/search.ts`) is the five parameters of `CrudListRequest`, and a
compile time check in that file keeps it equal to the generated contract. Paging, sorting and
searching are therefore the URL: a reload, a back button and a link somebody pasted into Discord all
land on the same page.

`deptParam` (`shared/api/department.ts`) is the only place that converts `ed` in the address bar to
`ED` in the contract. Params are handled as the parsed value everywhere else — `params={{ dept }}`
on a `<Link>` takes the enum, and `stringify` writes the URL.

`filter[ownerDepartment]` is not a search parameter. It is not in the contract either, because its
names are the properties of the entity; `listQuerySerializer` is the one place that spells it, and
the server refuses a name outside `CrudOptions.Filterable` with a 400.

The component then wires the route to `DataList`:

```tsx
const search = Route.useSearch();
const navigate = Route.useNavigate();

<DataList
  search={search}
  onSearchChange={(patch) => void navigate({ search: (previous) => ({ ...previous, ...patch }) })}
  ...
/>
```

Two lines, and they are the reason `DataList` takes `search` and `onSearchChange` rather than the
route object the design sketched: a generic component that reached into the router would have to
widen the search parameters back to `unknown`, which is exactly the typing this recipe exists for.
There is still no table markup in a route file.

## Recipe 3 — a public detail page

```tsx
export const Route = createFileRoute('/_public/$slug')({
  loader: ({ context, params }) =>
    context.queryClient.ensureQueryData(publicContentQuery('Page', params.slug)),
  notFoundComponent: NotFound,
  errorComponent: NotFound,
  component: PublicContentPage,
});
```

Load in the loader, never in the component, and give the route its own `notFoundComponent` so a
slug that does not exist is a page and not an error boundary. `errorComponent` is there for the
same reason: the API answers 404 for a page that is not published, which reaches the router as a
thrown `ApiError` rather than as a not-found.

The static routes of `_public/` win over this one, so `/forbidden` stays `/forbidden`: a page an
editor creates cannot take an address the application already owns.

## Layout of the folder

| Path                       | What it is                                                   |
| -------------------------- | ------------------------------------------------------------ |
| `__root.tsx`               | Context, and the 404 for an address no layout claims         |
| `_public.tsx` + `_public/` | Open to anybody: the home page, `/login-error`, `/forbidden` |
| `_member.tsx` + `_member/` | Signed in: `/me`                                             |
| `_staff.tsx` + `_staff/`   | Back office: `/staff/*`, with the department sidebar         |

A layout route is pathless (`_public`), so the addresses stay `/`, `/me`, `/staff/ed/links`. Under
`_staff/`, a file named `staff.$dept.links.tsx` is the route `/staff/$dept/links`.

Guards are the only authorisation in the client, and they are convenience, not security: every one
of them is answered again by the server, which is what actually decides.
